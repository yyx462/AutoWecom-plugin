①整台机器：一次场景运行的闭环

1

场景即合同 scenarios/s1–s5.md

每个场景一份 Markdown：用户原话 prompt + expect/forbid 字面清单。放在目标 skill 自己的源码树里，和 skill 同一个 PR 演进。

2

藏起答案 stash-scenarios.sh

spawn 前把 scenarios/ 搬出子代理的视野——run 1 证明：冷启动子代理探索 skill 目录时真的会把自己的考卷读一遍。

3

上膛备份 reset.sh arm

cp -Rp ~/.config/log-labor → ~/.yyxSkill/state/log-labor/latest/（0600，永不回显 key），并写入 armed.json。

4

spawn 冷启动子代理 task tool

prompt 只有用户原话，一字不加。找到并遵循 skill 本身就是考题。守门插件 yyx-skill-test-guard.js 在 task 前后挂钩子：前→补快照，后→自动 restore + disarm，想跳过备份都不可能。

5

取证 fetch-session.sh

从 opencode.db 只读定位该子代理 session，导出 transcript.json，连同 scenario.md 一起存进 runs/——证据不入仓库。

6

零 LLM 评分 grade.py

门：expect 全命中、forbid 零命中（forbid 只查执行过的命令）、有像样的最终答复。赘肉：tool_calls / reasoning tokens / overthink 段。哨兵：--skill-file 双向比对“被喂的 skill 正文 vs 磁盘”——本日最大的发现就靠它。

7

复位 reset.sh restore

配置打回快照原样，doctor 验健康，卸膛。下个场景从净土开始。

③一句总结

机器负责取证、复位、拦鬼；子代理负责犯真实的错；评分器负责把错误变成数字。今天净收益：s1 从 7 步臟写收敛到 2 步停手，一个会打回 skill 文件的 CLI bug 落网，评分器学会了辨认幽灵。遗留一件：重建 log-labor 二进制（go build ./cmd/log-labor），别让嵌入式旧 skill 再咬人。
